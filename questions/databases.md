1. Как настроить master-slave репликацию в mysql (кратко)?

<details>
  <summary>Ответ</summary>

Необходимы 2 сервера: master и slave.

1. На обеих сервера устанавливаем сервер MySQL одинаковой версии.
2. Включаем сервер базы данных на обеих серверах.
3. Настраиваем master - в `/etc/my.cnf` устанавливаем слеюущие значения:
```
# выбираем ID сервера, произвольное число, лучше начинать с 1
server-id = 1
# путь к бинарному логу
log_bin = /var/log/mysql/mysql-bin.log
# название Вашей базы данных, которая будет реплицироваться
binlog_do_db = newdatabase
```
Перезапускаем сервер базы данных.
4. Подключаемся к master серверу, создаем пользователя и назначаем ему права для выполнения репликации.
```
mysql -u root -p <пароль root сервера БД>
GRANT REPLICATION SLAVE ON *.* TO 'slave_user'@'%' IDENTIFIED BY 'password';
FLUSH PRIVILEGES;
```
5. На master сервере делаем дамп базы данных c блокировкой таблиц.
```
mysqldump -u root -p --lock-all-tables newdatabase > newdatabase.sql
```
6. Переносим дамп базы на slave сервер, создаем базу данных с таким же именем и импортируем базу.
```
CREATE DATABASE newdatabase;
mysql -u root -p newdatabase < newdatabase.sql
```
7. Настраиваем slave в `/etc/my.cnf`:
```
# ID Слейва, удобно выбирать следующим числом после Мастера
server-id = 2
# Путь к relay логу
relay-log = /var/log/mysql/mysql-relay-bin.log
# Путь к bin логу на Мастере
log_bin = /var/log/mysql/mysql-bin.log
# База данных для репликации
binlog_do_db = newdatabase
```
Перезапускаем сервер базы данных.
8. Запускаем репликацию на slave сервере.
```
CHANGE MASTER TO MASTER_HOST='10.10.0.1', MASTER_USER='slave_user', MASTER_PASSWORD='password',
MASTER_LOG_FILE = 'mysql-bin.000001', MASTER_LOG_POS = 107;
##Указанные значения мы берем из настроек Мастера
После этого запускаем репликацию на Слейве:
START SLAVE;
```
9. Проверяем статус репликации:
```
SHOW SLAVE STATUSG
```

</details>

3. Что такое VACUUM в PostgreSQL?

<details>
  <summary>Ответ</summary>

VACUUM высвобождает пространство, занимаемое «мёртвыми» кортежами. При обычных операциях PostgreSQL кортежи, удалённые или устаревшие в результате обновления, физически не удаляются из таблицы; они сохраняются в ней, пока не будет выполнена команда VACUUM. Таким образом, периодически необходимо выполнять VACUUM, особенно для часто изменяемых таблиц.

Без параметра команда VACUUM обрабатывает все таблицы в текущей базе данных, которые может очистить текущий пользователь. Если в параметре передаётся имя таблицы, VACUUM обрабатывает только эту таблицу.

Простая команда VACUUM (без FULL) только высвобождает пространство и делает его доступным для повторного использования. Эта форма команды может работать параллельно с обычными операциями чтения и записи таблицы, так она не требует исключительной блокировки. Однако освобождённое место не возвращается операционной системе (в большинстве случаев); оно просто остаётся доступным для размещения данных этой же таблицы. VACUUM FULL переписывает всё содержимое таблицы в новый файл на диске, не содержащий ничего лишнего, что позволяет возвратить неиспользованное пространство операционной системе. Эта форма работает намного медленнее и запрашивает исключительную блокировку для каждой обрабатываемой таблицы.

</details>

4. Что означает ACID?

<details>
  <summary>Ответ</summary>

ACID — четыре гарантии транзакций в СУБД:
- **Atomicity (атомарность)** — транзакция выполняется целиком или не выполняется совсем: при ошибке или `ROLLBACK` все её изменения отменяются.
- **Consistency (согласованность)** — транзакция переводит БД из одного корректного состояния в другое: соблюдаются ограничения (PK, FK, CHECK, UNIQUE).
- **Isolation (изоляция)** — параллельные транзакции не мешают друг другу; степень изоляции задаётся уровнем изоляции.
- **Durability (долговечность)** — после `COMMIT` данные не теряются даже при падении сервера. В PostgreSQL это обеспечивает WAL и `fsync`; параметр `synchronous_commit = off` ускоряет запись ценой возможной потери последних транзакций при сбое.

</details>

5. Какие есть уровни изоляции транзакций и какие аномалии они допускают?

<details>
  <summary>Ответ</summary>

Аномалии:
- **dirty read** — чтение незафиксированных данных другой транзакции;
- **non-repeatable read** — повторное чтение строки даёт другое значение;
- **phantom read** — повторный запрос с условием возвращает другой набор строк;
- **serialization anomaly** (например, write skew) — результат не соответствует ни одному последовательному порядку выполнения.

| Уровень | Dirty | Non-repeatable | Phantom | Serialization |
|---|---|---|---|---|
| Read Uncommitted | по стандарту возможно | да | да | да |
| Read Committed | нет | да | да | да |
| Repeatable Read | нет | нет | по стандарту возможно | да |
| Serializable | нет | нет | нет | нет |

Особенности PostgreSQL: по умолчанию `READ COMMITTED`; `READ UNCOMMITTED` ведёт себя как `READ COMMITTED` (грязного чтения нет вообще); `REPEATABLE READ` реализован как snapshot isolation и фантомов тоже не допускает; `SERIALIZABLE` (SSI) может прерывать транзакции с ошибкой сериализации — приложение должно уметь их повторять. В MySQL InnoDB по умолчанию `REPEATABLE READ`.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
```

</details>

6. Как работает MVCC в PostgreSQL и зачем нужен autovacuum?

<details>
  <summary>Ответ</summary>

MVCC (Multi-Version Concurrency Control) — каждая строка хранится в виде версий (кортежей) со служебными полями `xmin` (какая транзакция создала версию) и `xmax` (какая удалила). `UPDATE` не перезаписывает строку, а создаёт новую версию и помечает старую; `DELETE` только проставляет `xmax`. Каждая транзакция видит снимок данных (snapshot), поэтому читатели не блокируют писателей и наоборот.

Обратная сторона — накапливаются «мёртвые» версии, которые больше никому не видны. Autovacuum — фоновый процесс, который:
- запускает `VACUUM` для таблиц, где мёртвых строк больше `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples` (по умолчанию 50 + 20%);
- запускает `ANALYZE` для обновления статистики планировщика;
- «замораживает» старые строки (freeze), защищая от переполнения 32-битного счётчика транзакций (transaction ID wraparound). Если заморозка не успевает, PostgreSQL в итоге перестаёт выполнять пишущие транзакции.

Отключать autovacuum нельзя; для больших, часто изменяемых таблиц его наоборот настраивают агрессивнее (уменьшают `scale_factor` на уровне таблицы). Главный враг VACUUM — долгие транзакции и забытые `idle in transaction`: они удерживают старый снимок, и мёртвые строки нельзя удалить.

```sql
SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
SELECT datname, age(datfrozenxid) FROM pg_database;
```

</details>

7. Что такое bloat в PostgreSQL и как с ним бороться?

<details>
  <summary>Ответ</summary>

Bloat («раздувание») — таблицы и индексы занимают на диске существенно больше места, чем нужно для живых данных, из-за пустого места от мёртвых строк. Последствия: больше I/O, хуже попадание в кэш, медленнее последовательные сканы и бэкапы.

Причины: autovacuum не успевает или ему мешают долгие транзакции, неактивные слоты репликации, массовые `UPDATE`/`DELETE`.

Как обнаружить: расширение `pgstattuple`, оценочные запросы (например, из pgexperts / check_postgres), метрики postgres_exporter, рост `n_dead_tup` в `pg_stat_user_tables`.

Как убрать:
- `VACUUM FULL` / `CLUSTER` — переписывают таблицу, но берут эксклюзивную блокировку (таблица недоступна);
- `pg_repack` или `pg_squeeze` — перестраивают таблицу онлайн с короткой блокировкой в конце;
- для индексов — `REINDEX INDEX CONCURRENTLY`.

Профилактика: тюнинг autovacuum, контроль долгих транзакций (`idle_in_transaction_session_timeout`), `fillfactor` < 100 для часто обновляемых таблиц (чтобы работали HOT-обновления).

</details>

8. Какие типы индексов есть в PostgreSQL и когда какой использовать?

<details>
  <summary>Ответ</summary>

- **B-tree** — индекс по умолчанию: равенство, диапазоны (`<`, `>`, `BETWEEN`), сортировка, `LIKE 'abc%'` (при подходящей collation или `text_pattern_ops`).
- **Hash** — только равенство; нужен редко.
- **GIN** — «обратный» индекс для составных значений: `jsonb` (`@>`, `?`), массивы, полнотекстовый поиск (`tsvector`), триграммы (`pg_trgm`) для `LIKE '%abc%'`.
- **GiST / SP-GiST** — геоданные (PostGIS), диапазоны, ближайшие соседи, exclusion constraints.
- **BRIN** — очень компактный индекс по диапазонам блоков для огромных таблиц, где данные физически упорядочены (логи, time series по времени вставки).

Полезные разновидности: составные индексы (важен порядок колонок), частичные (`WHERE status = 'active'`), по выражению (`lower(email)`), покрывающие (`INCLUDE`) для index-only scan.

```sql
CREATE INDEX CONCURRENTLY idx_orders_user ON orders (user_id, created_at);
CREATE INDEX CONCURRENTLY idx_docs_data ON docs USING gin (data jsonb_path_ops);
```

Каждый индекс замедляет запись и занимает место, поэтому неиспользуемые индексы стоит находить (`pg_stat_user_indexes.idx_scan = 0`) и удалять.

</details>

9. Почему PostgreSQL может не использовать индекс?

<details>
  <summary>Ответ</summary>

- **Низкая селективность** — запрос возвращает большую долю таблицы, и Seq Scan дешевле случайного чтения по индексу. Это нормальное решение планировщика.
- **Устаревшая статистика** — давно не было `ANALYZE`, планировщик ошибается в оценке числа строк.
- **Функция или приведение типа над колонкой**: `WHERE lower(email) = ...` или `WHERE created_at::date = ...` не используют обычный индекс по колонке — нужен индекс по выражению или переписанное условие.
- **Несовпадение типов** (например, сравнение `bigint` с `numeric`, текст с числом).
- **`LIKE '%abc'`** — ведущий шаблон; B-tree не поможет, нужен GIN с `pg_trgm`.
- **Составной индекс** `(a, b)`, а в условии только `b`.
- **Маленькая таблица** — быстрее прочитать её целиком.
- Неподходящие параметры стоимости: для SSD стоит уменьшить `random_page_cost` (например, до 1.1), иначе планировщик переоценивает стоимость индексного доступа.

Проверка: `EXPLAIN (ANALYZE, BUFFERS)`; для эксперимента можно временно выполнить `SET enable_seqscan = off` в сессии (не в продакшн-конфиге).

</details>

10. Как читать EXPLAIN ANALYZE и как найти медленные запросы?

<details>
  <summary>Ответ</summary>

`EXPLAIN` показывает план запроса с оценками, `EXPLAIN ANALYZE` реально выполняет запрос и добавляет фактическое время и число строк (для `UPDATE`/`DELETE` — оборачивать в транзакцию с `ROLLBACK`).

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
```

На что смотреть:
- тип узлов: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`; соединения `Nested Loop`, `Hash Join`, `Merge Join`;
- расхождение `rows` (оценка) и `actual rows` — признак плохой статистики;
- `loops` — время узла умножается на число повторов;
- `Buffers: shared hit/read` — сколько страниц из кэша, а сколько с диска;
- `Sort Method: external merge Disk` — сортировке не хватило `work_mem`.

Поиск медленных запросов:
- расширение `pg_stat_statements` — агрегированная статистика по запросам (суммарное и среднее время, число вызовов);
- `log_min_duration_statement = 500ms` — логирование медленных запросов, анализ через pgBadger;
- `auto_explain` — автоматическое логирование планов медленных запросов;
- `pg_stat_activity` — что выполняется прямо сейчас.

```sql
SELECT query, calls, total_exec_time, mean_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
```

</details>

11. Что такое WAL в PostgreSQL?

<details>
  <summary>Ответ</summary>

WAL (Write-Ahead Log, журнал упреждающей записи) — журнал, в который любое изменение данных записывается до того, как изменённые страницы попадут в файлы таблиц. При `COMMIT` достаточно сбросить на диск WAL (последовательная запись — быстро), а сами страницы записываются позже фоново.

Зачем нужен:
- **восстановление после сбоя** — при старте PostgreSQL проигрывает WAL от последней контрольной точки (checkpoint);
- **репликация** — реплики получают и применяют поток WAL;
- **PITR** — архив WAL вместе с базовым бэкапом позволяет восстановиться на любой момент времени.

Хранится в `pg_wal/` сегментами по 16 МБ. Важные параметры: `wal_level` (`replica` / `logical`), `max_wal_size`, `checkpoint_timeout`, `archive_mode` / `archive_command`. Частая авария: `pg_wal` переполняет диск из-за сломанного `archive_command` или неактивного слота репликации, который удерживает сегменты (ограничивается `max_slot_wal_keep_size`).

</details>

12. Чем физическая репликация отличается от логической в PostgreSQL?

<details>
  <summary>Ответ</summary>

**Физическая (streaming) репликация** — реплика получает поток WAL и побайтово применяет его:
- копия всего кластера целиком (все базы), нельзя выбрать отдельные таблицы;
- одинаковая мажорная версия и архитектура;
- реплика только для чтения (hot standby);
- основной механизм для HA и failover.

**Логическая репликация** — передаются логические изменения строк (INSERT/UPDATE/DELETE) через публикации и подписки:
- можно реплицировать отдельные таблицы, фильтровать строки и колонки;
- работает между разными мажорными версиями — используется для апгрейда с минимальным даунтаймом и миграций;
- подписчик — обычная пишущая база;
- не реплицируются DDL и значения последовательностей, у таблиц нужен первичный ключ (или `REPLICA IDENTITY`).

```sql
-- на источнике (wal_level = logical)
CREATE PUBLICATION pub_orders FOR TABLE orders;
-- на приёмнике
CREATE SUBSCRIPTION sub_orders CONNECTION 'host=src dbname=app user=repl' PUBLICATION pub_orders;
```

</details>

13. Синхронная и асинхронная репликация: в чём разница и как контролировать отставание реплики?

<details>
  <summary>Ответ</summary>

- **Асинхронная** (по умолчанию) — мастер подтверждает `COMMIT`, не дожидаясь реплик. Быстро, но при падении мастера последние транзакции могут быть потеряны (RPO > 0).
- **Синхронная** — `COMMIT` подтверждается только после ответа реплик из `synchronous_standby_names` (например, `ANY 1 (replica1, replica2)`). Степень гарантии задаёт `synchronous_commit`: `remote_write`, `on` (WAL сброшен на диск реплики), `remote_apply` (изменение уже видно на реплике). Плата — рост задержки записи и риск остановки записей, если синхронная реплика недоступна (поэтому нужно минимум две кандидатуры).

Отставание (lag) на мастере:
```sql
SELECT application_name, state, sync_state, write_lag, flush_lag, replay_lag,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;
```
На реплике: `SELECT now() - pg_last_xact_replay_timestamp();`

Причины лага: медленный диск или сеть реплики, тяжёлые запросы на реплике (конфликты с recovery), массовые изменения на мастере. Лаг нужно мониторить и алертить — приложение, читающее с реплики, может видеть устаревшие данные.

</details>

14. Как организовать автоматический failover PostgreSQL с помощью Patroni и etcd?

<details>
  <summary>Ответ</summary>

Patroni — демон, который работает рядом с каждым экземпляром PostgreSQL и управляет им, используя распределённое хранилище конфигурации (DCS: etcd, Consul, ZooKeeper или Kubernetes API) для выбора лидера.

Как работает:
- лидер держит в etcd ключ-блокировку (leader key) с TTL и регулярно его продлевает;
- если лидер пропал и ключ истёк, реплики проверяют своё отставание, и наиболее актуальная, получившая ключ, промоутится в primary; остальные переключаются на неё;
- бывший лидер, не сумевший продлить ключ (например, потерял связь с etcd), сам понижает себя до реплики — защита от split-brain; дополнительно можно включить watchdog;
- etcd должен иметь нечётное число узлов (3 или 5) для кворума.

Клиенты находят текущий primary через HAProxy, который проверяет REST API Patroni (порт 8008, `/primary`, `/replica`), либо через vip-manager / Consul DNS.

```bash
patronictl -c /etc/patroni/patroni.yml list
patronictl -c /etc/patroni/patroni.yml switchover   # плановое переключение
```

Для нулевой потери данных при failover используют `synchronous_mode: true`.

</details>

15. Зачем нужен пулер соединений (PgBouncer) и почему много подключений к PostgreSQL — плохо?

<details>
  <summary>Ответ</summary>

В PostgreSQL каждое подключение — отдельный процесс ОС (backend) со своей памятью. Тысячи соединений означают расход памяти (особенно с учётом `work_mem` на операцию), накладные расходы на переключение контекста, конкуренцию за блокировки и снимки. Производительность падает задолго до достижения `max_connections`, хотя реально одновременно работающих запросов обычно немного (порядка числа ядер).

PgBouncer держит небольшой пул реальных подключений к базе и раздаёт их множеству клиентских соединений. Режимы:
- **session** — серверное соединение закрепляется за клиентом на всю сессию (меньше всего выгоды);
- **transaction** — соединение выдаётся на время транзакции; самый популярный режим. Ограничения: нельзя полагаться на состояние сессии (`SET`, advisory locks, `LISTEN/NOTIFY`, временные таблицы); prepared statements поддерживаются с версии 1.21 (`max_prepared_statements`);
- **statement** — на один запрос, транзакции из нескольких запросов запрещены.

Альтернативы: Odyssey, PgCat, пулы на стороне приложения (HikariCP и т.п.). Пулер также сглаживает всплески подключений при массовом рестарте подов.

</details>

16. Какие способы резервного копирования PostgreSQL вы знаете? Что такое PITR?

<details>
  <summary>Ответ</summary>

- **pg_dump / pg_dumpall** — логический бэкап (SQL или custom-формат) одной базы; можно восстанавливать отдельные таблицы и переносить между версиями. Минусы: медленно на больших базах, восстанавливает только состояние на момент дампа.
- **pg_basebackup** — физическая копия всего кластера через протокол репликации; основа для реплики или PITR. С PostgreSQL 17 поддерживает инкрементальные бэкапы (`--incremental` + `pg_combinebackup`).
- **pgBackRest, WAL-G, Barman** — инструменты для продакшна: полные, дифференциальные и инкрементальные бэкапы, параллельность, сжатие, шифрование, хранение в S3, архивация WAL, проверка и удобное восстановление.

**PITR (Point-In-Time Recovery)** — восстановление на произвольный момент: берётся базовый физический бэкап и поверх проигрывается архив WAL до нужной точки. Позволяет откатиться, например, на момент перед ошибочным `DELETE`.

```ini
# postgresql.conf при восстановлении + файл recovery.signal
restore_command = 'pgbackrest --stanza=main archive-get %f "%p"'
recovery_target_time = '2026-09-20 14:30:00+03'
```

Бэкап, который ни разу не восстанавливали, не считается бэкапом: восстановление нужно регулярно проверять.

</details>

17. Какие блокировки бывают в PostgreSQL и что такое deadlock?

<details>
  <summary>Ответ</summary>

- **Блокировки строк** — `UPDATE`/`DELETE`/`SELECT ... FOR UPDATE` блокируют изменяемые строки до конца транзакции; чтение их не блокирует (MVCC).
- **Блокировки таблиц** — от `ACCESS SHARE` (обычный `SELECT`) до `ACCESS EXCLUSIVE` (`ALTER TABLE`, `DROP`, `VACUUM FULL`, `TRUNCATE`), которая блокирует даже чтение.
- **Advisory locks** — пользовательские блокировки, которые приложение ставит само (`pg_advisory_lock`).

Опасный сценарий: `ALTER TABLE` ждёт завершения долгого запроса, а все новые запросы к таблице встают в очередь за ним — сервис «лежит». Поэтому для DDL задают `SET lock_timeout = '5s'`.

**Deadlock** — две транзакции ждут друг друга: T1 заблокировала строку A и ждёт B, T2 заблокировала B и ждёт A. PostgreSQL через `deadlock_timeout` (1 с) проверяет граф ожиданий и прерывает одну из транзакций с ошибкой. Профилактика: блокировать ресурсы в одном и том же порядке, делать транзакции короткими.

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, state, query
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

</details>

18. Как проводить миграции схемы БД без даунтайма?

<details>
  <summary>Ответ</summary>

Основной принцип — **expand / contract** (расширить, затем сузить): схема какое-то время совместима и со старой, и с новой версией приложения.
1. Добавить новую колонку/таблицу (expand), не ломая старый код.
2. Выкатить код, который пишет в оба места, заполнить данные батчами.
3. Переключить чтение на новую структуру.
4. Когда старый код полностью выведен — удалить старое (contract).

Приёмы для PostgreSQL:
- индексы — только `CREATE INDEX CONCURRENTLY`;
- `ADD COLUMN ... DEFAULT <константа>` мгновенный с PG 11, но смена типа колонки переписывает таблицу;
- `NOT NULL` и внешние ключи — через `ADD CONSTRAINT ... NOT VALID`, затем `VALIDATE CONSTRAINT` (без долгой эксклюзивной блокировки);
- всегда `SET lock_timeout` и повтор при неудаче;
- большие `UPDATE` — батчами, чтобы не раздувать WAL, лаг реплик и bloat;
- переименование колонок — через новую колонку, а не `RENAME` в один шаг.

Инструменты: Flyway, Liquibase, миграции фреймворков; для MySQL — gh-ost, pt-online-schema-change.

</details>

19. Чем партиционирование отличается от шардинга?

<details>
  <summary>Ответ</summary>

- **Партиционирование** — разбиение большой таблицы на части (партиции) внутри одного сервера. В PostgreSQL — декларативное: `PARTITION BY RANGE / LIST / HASH`. Плюсы: запросы с условием по ключу читают только нужные партиции (partition pruning), старые данные удаляются мгновенно через `DROP` / `DETACH PARTITION` вместо массового `DELETE`, VACUUM и индексы работают с меньшими объёмами.
- **Шардинг** — распределение данных по нескольким серверам (шардам) по ключу шардирования (например, `user_id`). Масштабирует запись и объём сверх возможностей одного сервера. Сложности: выбор ключа, межшардовые запросы и транзакции, решардинг, бэкапы и консистентность. Реализации: Citus, Vitess (MySQL), шардинг на уровне приложения, встроенный в MongoDB / Cassandra.

```sql
CREATE TABLE events (id bigint, created_at timestamptz, payload jsonb) PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_09 PARTITION OF events FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Шардинг — крайняя мера: сначала вертикальное масштабирование, индексы и запросы, реплики для чтения, кэш, партиционирование.

</details>

20. Чем SQL-базы отличаются от NoSQL? Когда выбирать Redis или MongoDB?

<details>
  <summary>Ответ</summary>

**SQL (реляционные: PostgreSQL, MySQL)** — строгая схема, связи между таблицами, JOIN, ACID-транзакции, мощный язык запросов. Масштабируются в основном вертикально и репликами для чтения.

**NoSQL** — общее название нереляционных хранилищ, обычно гибкая схема и горизонтальное масштабирование, часто ценой ослабленной согласованности. Основные типы:
- **key-value** — Redis / Valkey, etcd: кэш, сессии, счётчики, очереди, rate limiting, распределённые блокировки;
- **документные** — MongoDB: JSON-подобные документы с гибкой схемой, встроенные репликация (replica set) и шардинг; удобно, когда данные естественно объединяются в документ;
- **колоночные / wide-column** — Cassandra, ScyllaDB: огромные объёмы записи, распределённость;
- **time series** — Prometheus TSDB, VictoriaMetrics, InfluxDB;
- **графовые** — Neo4j.

Выбор определяется моделью данных и паттерном доступа. Граница размыта: PostgreSQL с `jsonb` закрывает многие «документные» задачи, а MongoDB поддерживает многодокументные транзакции.

</details>

21. Как Redis сохраняет данные на диск и что происходит при нехватке памяти?

<details>
  <summary>Ответ</summary>

Redis хранит данные в памяти, персистентность опциональна:
- **RDB** — периодический снимок всего датасета (`save 3600 1 300 100`, `BGSAVE`), делается в дочернем процессе через `fork()` (copy-on-write, поэтому нужен запас памяти). Компактный файл, быстрый рестарт, но теряются изменения с последнего снимка.
- **AOF** (append only file) — журнал всех пишущих команд; `appendfsync always / everysec / no` задаёт баланс надёжности и скорости (`everysec` — потеря до ~1 с). Файл периодически перезаписывается (AOF rewrite).
- Обычно включают оба механизма или AOF с RDB-преамбулой (`aof-use-rdb-preamble yes`); для чистого кэша персистентность можно отключить.

При достижении `maxmemory` работает политика вытеснения `maxmemory-policy`:
- `noeviction` (по умолчанию) — ошибка на запись;
- `allkeys-lru` / `allkeys-lfu` — вытеснять наименее недавно / наименее часто используемые ключи (типично для кэша);
- `volatile-lru` / `volatile-lfu` / `volatile-ttl` / `volatile-random` — только среди ключей с TTL;
- `allkeys-random`.

Отказоустойчивость: репликация + Redis Sentinel или Redis Cluster (шардинг по 16384 слотам). После смены лицензии Redis в 2024 году появился форк Valkey (Linux Foundation), совместимый по протоколу; с Redis 8 доступна также лицензия AGPLv3.

</details>

22. Какие варианты репликации есть в MySQL и что в ней изменилось в новых версиях?

<details>
  <summary>Ответ</summary>

Базовая схема (source → replica через binlog) описана в вопросе 1; дополнительно стоит знать:
- **Форматы binlog**: `STATEMENT`, `ROW` (по умолчанию и рекомендуемый), `MIXED`.
- **GTID** (`gtid_mode = ON`, `enforce_gtid_consistency = ON`) — глобальные идентификаторы транзакций: реплика сама знает, что уже применила, переключение на другой источник делается через `SOURCE_AUTO_POSITION = 1` без поиска файла и позиции.
- **Асинхронная** (по умолчанию) и **полусинхронная** (semi-sync) репликация — источник ждёт подтверждения получения транзакции хотя бы одной репликой.
- **Group Replication / InnoDB Cluster** — кластер с автоматическим выбором primary и failover (вместе с MySQL Router); альтернатива — Galera (Percona XtraDB Cluster, MariaDB).
- Параллельное применение на реплике: `replica_parallel_workers`.

Терминология: начиная с 8.0.22–8.0.26 используются `CHANGE REPLICATION SOURCE TO`, `START REPLICA`, `SHOW REPLICA STATUS`; старые формы с `MASTER`/`SLAVE` объявлены устаревшими, а в MySQL 8.4 LTS большинство из них удалено. Отставание смотрят в `SHOW REPLICA STATUS\G` (`Seconds_Behind_Source`) или через pt-heartbeat.

</details>
